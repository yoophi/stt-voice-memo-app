# Feature Specification: Mobile Tauri App Foundation

**Feature Branch**: `main`

**Created**: 2026-08-15

**Status**: Draft

**Input**: User description: "Specify 스킬을 이용하여 모바일 우선 Tauri 앱을 초기화한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Run the Mobile App Shell (Priority: P1)

개발자는 새 checkout에서 프로젝트 의존성을 준비하고 iOS와 Android 기기에서 앱을
실행해 STT Voice Memo의 초기 화면을 확인할 수 있다. 초기 화면은 앱의 정체성과 개발
준비 상태를 명확히 보여주며 아직 제공하지 않는 녹음 기능을 작동하는 것처럼 표시하지 않는다.

**Why this priority**: 모바일 앱이 두 우선 플랫폼에서 실행되지 않으면 이후 녹음, 변환,
메모 기능을 독립적으로 개발하거나 검증할 기반이 없다.

**Independent Test**: 준비된 개발 환경의 새 checkout에서 문서화된 절차만 따라 iOS와
Android 실제 기기에 앱을 설치하고 초기 화면이 오류 없이 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 필수 모바일 개발 도구가 준비된 새 checkout, **When** 개발자가 문서화된
   초기 설정과 iOS 실행 절차를 수행하면, **Then** 실제 iOS 기기에 앱이 설치되고 초기
   화면이 표시된다.
2. **Given** 필수 모바일 개발 도구가 준비된 새 checkout, **When** 개발자가 문서화된
   초기 설정과 Android 실행 절차를 수행하면, **Then** 실제 Android 기기에 앱이 설치되고
   초기 화면이 표시된다.
3. **Given** 초기 앱을 처음 실행한 사용자, **When** 초기 화면이 열리면, **Then** 앱은
   마이크나 다른 민감한 시스템 권한을 요청하지 않는다.

### User Story 2 - Extend a Predictable Project Structure (Priority: P2)

개발자는 새 화면, 사용자 행동, 도메인 규칙 또는 플랫폼 연동을 추가할 위치를 프로젝트
구조와 문서만으로 판단할 수 있다. 기본 구조는 모바일 플랫폼 코드와 공유 비즈니스 규칙이
뒤섞이지 않도록 명확한 경계를 제공한다.

**Why this priority**: 초기 구조가 불명확하면 첫 녹음 기능부터 플랫폼 코드와 도메인 로직이
결합되어 이후 iOS, Android 및 데스크톱 확장이 어려워진다.

**Independent Test**: 개발자가 예시 변경 유형을 전달받아 화면, 사용자 행동, 도메인 규칙,
플랫폼 adapter 각각의 올바른 위치와 의존 방향을 문서에서 식별할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 초기화된 저장소, **When** 개발자가 프런트엔드 모듈 위치를 확인하면,
   **Then** 앱 조립, 화면, 위젯, 기능, 도메인 표현 및 공유 코드의 경계가 구분되어 있다.
2. **Given** 초기화된 저장소, **When** 개발자가 Rust 모듈 위치를 확인하면, **Then** 순수
   도메인, 유스케이스, port, 입력 adapter 및 infrastructure adapter의 경계가 구분되어 있다.
3. **Given** 아직 원격 또는 녹음 상태가 없는 초기 앱, **When** 개발자가 상태 구성을
   확인하면, **Then** 비어 있는 비즈니스 상태를 중복 저장하지 않고 향후 상태 소유권을
   적용할 단일 조립 지점만 제공한다.

### User Story 3 - Validate the Foundation Consistently (Priority: P3)

개발자는 기능 개발을 시작하기 전에 동일한 검증 절차로 소스 형식, 정적 검사, 자동 테스트
및 모바일 빌드 준비 상태를 확인할 수 있다. 필수 도구가 없거나 설정이 잘못되면 실패 원인과
다음 조치를 알 수 있다.

**Why this priority**: 재현 가능한 검증 기준이 있어야 이후 기능 변경이 모바일 앱 기반을
손상했는지 빠르게 판단할 수 있다.

**Independent Test**: 정상 환경과 필수 도구 하나가 누락된 환경에서 각각 검증 절차를
실행해 성공 결과와 실행 가능한 오류 안내가 제공되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 올바르게 준비된 저장소, **When** 개발자가 전체 기본 검증 절차를 실행하면,
   **Then** 모든 검사가 오류 없이 완료된다.
2. **Given** 필수 플랫폼 도구가 누락된 환경, **When** 개발자가 해당 모바일 실행 또는
   검증 절차를 수행하면, **Then** 누락된 항목과 해결 방법을 식별할 수 있는 오류가 표시된다.
3. **Given** 의존성 설치가 중단된 저장소, **When** 개발자가 설치 절차를 다시 수행하면,
   **Then** 저장소를 삭제하거나 수동으로 생성 파일을 정리하지 않고 복구할 수 있다.

### Edge Cases

- iOS 또는 Android 개발 도구 중 한쪽만 설치된 환경에서는 준비된 플랫폼의 작업은
  계속할 수 있고, 준비되지 않은 플랫폼만 명확한 사전 조건 오류로 중단된다.
- 의존성 설치가 중간에 종료되거나 캐시가 불완전해도 같은 설치 절차를 안전하게 재실행할
  수 있다.
- 개발 서버 포트가 이미 사용 중이면 충돌 원인을 표시하고 다른 포트 사용 또는 기존
  프로세스 종료 방법을 제공한다.
- 앱이 시작 도중 background로 이동하거나 다시 foreground로 돌아와도 초기 화면이
  손상되거나 민감한 권한을 요청하지 않는다.
- 작은 휴대전화 화면, 화면 회전 및 safe-area가 있는 기기에서도 핵심 초기 화면이
  잘리거나 조작 불가능해지지 않는다.
- 생성된 모바일 프로젝트 파일이 누락된 경우 재생성 절차가 수동 파일 복사를 요구하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 저장소는 새 checkout에서 반복 실행 가능한 하나의 문서화된 초기 설정
  절차를 제공해야 한다.
- **FR-002**: 프로젝트는 iOS와 Android 개발 대상에서 설치 및 실행 가능한 초기 앱을
  제공해야 한다.
- **FR-003**: 초기 화면은 `STT Voice Memo` 제품명을 표시하고 앱 기반이 정상 실행 중임을
  사용자가 이해할 수 있게 해야 한다.
- **FR-004**: 초기 화면은 휴대전화 크기, safe-area 및 세로·가로 방향에서 주요 콘텐츠와
  조작 영역을 사용할 수 있어야 한다.
- **FR-005**: 저장소는 프런트엔드의 앱 조립, 화면, 위젯, 사용자 기능, 도메인 표현 및
  공유 코드 영역을 구분해야 한다.
- **FR-006**: 저장소는 Rust의 도메인, 유스케이스, port, 입력 adapter 및 infrastructure
  adapter 영역을 구분해야 한다.
- **FR-007**: 프로젝트는 형식 검사, 정적 검사, 자동 테스트 및 지원되는 모바일 대상의
  빌드 준비 상태를 확인하는 문서화된 검증 절차를 제공해야 한다.
- **FR-008**: 의존성 및 프로젝트 설정은 동일한 checkout에서 반복 설치했을 때 동일한
  앱 기반을 재현해야 한다.
- **FR-009**: 모바일 실행에 필요한 외부 도구가 누락된 경우 실패한 단계, 누락된 사전 조건
  및 개발자가 취할 수 있는 다음 조치를 알려야 한다.
- **FR-010**: 초기 앱과 저장소에는 API 키, 사용자 자격 증명 또는 배포용 비밀 값이
  포함되어서는 안 된다.
- **FR-011**: 초기 앱은 마이크, 사진, 위치 또는 알림과 같은 민감한 런타임 권한을
  요청해서는 안 된다.
- **FR-012**: 녹음, 음성 변환, 메모 저장, 사용자 인증 및 백엔드 통신은 이 기능의 범위에
  포함하지 않아야 한다.
- **FR-013**: 데스크톱 배포 또는 데스크톱 전용 기능은 이 기능의 완료 조건이 아니어야 한다.

### Mobile and Lifecycle Requirements *(mandatory for affected features)*

- iOS와 Android는 동일한 제품 정체성과 초기 사용자 상태를 표시해야 하며 플랫폼별
  시작 절차와 필수 도구는 별도로 문서화해야 한다.
- 초기 앱은 녹음이나 네트워크 작업을 수행하지 않으므로 권한 거부, 오디오 인터럽트,
  오프라인 재시도 또는 업로드 취소 상태를 만들지 않아야 한다.
- 앱이 시작 중 background로 전환되거나 다시 활성화되어도 초기 화면으로 안전하게
  복귀해야 한다.
- 완료 검증에는 실제 iOS 기기 한 대와 실제 Android 기기 한 대가 포함되어야 한다.
- 데스크톱, 백그라운드 녹음 및 실시간 음성 변환은 후속 기능으로 유지해야 한다.

### Privacy and Data Lifecycle Requirements *(mandatory for audio/transcript features)*

- 이 기능은 오디오, 파생 오디오 또는 transcript를 생성, 전송 또는 저장하지 않아야 한다.
- 초기 앱은 provider 자격 증명을 요구하거나 클라이언트 설정에 보관하지 않아야 한다.
- 기본 로그는 로컬 개발 진단만 포함하고 사용자 콘텐츠나 환경의 비밀 값을 수집하지
  않아야 한다.

### Architecture Impact *(mandatory)*

- Rust 영역은 비어 있더라도 domain, application, ports, inbound 및 infrastructure
  경계를 확립해야 하며 외부 adapter가 domain/application에 역으로 의존해야 한다.
- React 영역은 app, pages, widgets, features, entities 및 shared 계층을 확립하고 하위
  계층이 상위 계층에 의존하지 않도록 해야 한다.
- 원격 비동기 상태의 조립 지점은 TanStack Query를 위한 단일 위치에 두되 아직 서버
  상태를 만들지 않아야 한다.
- 클라이언트 전용 상태는 필요할 때 Zustand가 소유하도록 준비하되 초기화만을 위해 빈
  전역 store나 중복 상태를 만들어서는 안 된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 필수 개발 도구가 준비된 새 checkout에서 SDK 다운로드 시간을 제외하고
  15분 이내에 첫 모바일 앱 실행을 완료할 수 있다.
- **SC-002**: 실제 iOS 및 Android 기기에서 각각 5회 연속 cold launch가 충돌이나 예상하지
  않은 권한 요청 없이 성공한다.
- **SC-003**: 문서화된 모든 기본 검증 절차가 깨끗한 checkout에서 100% 성공한다.
- **SC-004**: 프로젝트를 처음 보는 개발자가 화면, 사용자 기능, 도메인 규칙 및 플랫폼
  adapter의 추가 위치를 5분 이내에 올바르게 식별한다.
- **SC-005**: 지원하는 최소 휴대전화 viewport와 대표적인 iOS·Android 실제 기기에서
  초기 화면의 핵심 콘텐츠가 잘리거나 겹치지 않는다.
- **SC-006**: 필수 플랫폼 도구가 누락된 경우 개발자는 오류 출력만으로 2분 이내에 누락된
  항목과 다음 설치 단계를 식별할 수 있다.

## Assumptions

- 개발자는 iOS 검증을 위한 macOS, Xcode 및 실제 iOS 기기에 접근할 수 있다.
- 개발자는 Android SDK와 실제 Android 기기에 접근할 수 있다.
- 제품 표시 이름은 `STT Voice Memo`이며 배포 전까지 변경 가능한 안정적인 고유 앱
  식별자를 사용한다.
- 초기 앱은 단일 사용자용 로컬 shell이며 인증 또는 애플리케이션 백엔드를 요구하지 않는다.
- 이 기능은 프로젝트 기반만 만들며 녹음과 메모의 도메인 모델은 각 기능 명세에서 추가한다.
